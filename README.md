# 校车管理系统 · 开发与演示文档

[在线演示](https://sfenvd.github.io/BUS-FLUTTER/) · [GitHub Actions](https://github.com/SFENVD/BUS-FLUTTER/actions) · [课程综合报告](main.tex) · [Overleaf 交付包](overleaf.zip)

本文按当前源码整理，说明实际功能、开发方式、部署方式与现场演示步骤。核对日期：**2026-11-10**；演示准备面向 **2026-11-11**。项目是一个包含乘客、司机、管理员三种角色工作台的 **Flutter 演示应用**，主要业务交互已实现，数据来自本地样例，尚未接入真实业务后端。

**先看结论：可以演示预约选座、模拟支付与退款、信用扣分、司机任务与模拟定位、车辆司机管理、调度建议与确认，以及浏览器数据保存。不能演示真实付款、真实 GPS、跨设备同步或三角色共享同一订单的完整闭环。**

## 2. 当前功能完成情况

这里的“已实现”表示当前应用内可操作的功能，不代表已连接生产服务。

### 2.1 通用功能与乘客端

| 模块 | 已实现内容 | 当前边界 |
| --- | --- | --- |
| 登录与入口 | 固定账号登录、密码校验、角色匹配、退出、三角色切换、路由拦截 | 本地模拟认证，没有服务端鉴权 |
| 车次列表 | 路线、起终点、发车时间、票价、余座展示 | 来自预置车次，不是后台实时发布 |
| 预约选座 | 选择可用座位、生成预约、扣减可用座位；阻止重复预约、座位冲突、满座和已发车预约 | 无数据库事务与跨设备锁座 |
| 我的预约 | 全部、待发车、已完成、已取消筛选 | “已完成”含历史样例，新预约没有自动完成闭环 |
| 支付 | 选择微信／支付宝，支付中与已支付状态、保存模拟支付流水、重复提交保护 | 延迟 500ms 的模拟支付，无真实扣款；没有独立流水查询页面 |
| 取消与退款 | 取消待发车预约、释放座位；已支付取消后同步标记退款 | 无真实资金退款 |
| 信用 | 信用分、信用等级、取消记录与扣分；重登保留分数 | 未实现低分禁止预约、奖励或申诉恢复机制 |
| 通知 | 预约、支付、取消生成应用内消息，未读计数与全部已读 | 本地通知，无短信或系统推送；列表未按角色／用户隔离 |

### 2.2 司机端

| 模块 | 已实现内容 | 当前边界 |
| --- | --- | --- |
| 今日任务 | 路线、车次、车辆、时间、人数、里程与状态 | 任务是独立样例，不接收后台新调度 |
| 乘客名单 | 展开姓名、手机尾号、上车点和座位号 | 不读取乘客端新创建的预约 |
| 任务流程 | 待发车 → 行程中 → 已完成；同时只能启动一个任务 | 无司机接单／拒单、验票或上车签到 |
| 位置共享 | 启动时立即生成位置，每 5 秒更新，可手动上报；完成、退出或切角色后停止 | Timer 模拟坐标与速度，无 GPS 或网络上传 |
| 恢复任务 | 重登后可恢复进行中任务的位置模拟 | 依赖本地业务快照 |
| 运营统计 | 日／周／月切换，班次、人数、里程、准点率展示 | 固定统计样例，不随本次完成任务累加 |

### 2.3 后台管理端

| 模块 | 已实现内容 | 当前边界 |
| --- | --- | --- |
| 总览 | 在线、空闲、维修车辆、司机数、待调度人数随后台状态变化 | 仅反映后台业务域 |
| 车辆管理 | 新增、编辑、删除；车牌重复、必填、座位数校验；运行中禁止删除 | 本地数据维护 |
| 司机管理 | 新增、编辑、删除、绑定车辆；手机号重复与绑定冲突校验 | 管理资料与登录账号是两套数据 |
| 人工调度 | 选择需求、车辆、司机，生成待确认方案 | 需求来自样例，未提供需求新增编辑界面 |
| “AI 生成方案” | 按需求人数降序，匹配空闲、有绑定司机且容量足够的车辆 | 本地贪心算法，无大模型调用、路线优化或全局最优保证 |
| 确认生效 | 重验需求时间、容量、占用、绑定和建议快照，再更新需求与车辆状态 | 不创建乘客车次或司机任务；无调度取消／完成闭环 |
| 位置监控 | 自绘网格、车辆标记、司机、速度、坐标、更新时间；自动与手动刷新 | 无地图 SDK、真实 GPS 或 WebSocket |
| 客户 ETA | 展示预计到达时间卡片 | 固定示例，未按坐标、路况计算 |
| 历史分析 | 日／周／月、人数、收入、利用率、趋势、路线排行 | 固定统计样例，不根据三端实际操作汇总 |

### 2.4 尚未实现的主要能力

1. **统一后端与三端联动**：乘客预约汇总为后台需求、后台派车生成司机任务、司机完成后更新乘客订单，这条链路尚未接通。
2. **真实身份与权限服务**：注册、验证码、找回密码、服务端会话和权限校验均未接入。前端路由拦截不能替代服务端权限控制。
3. **真实支付与结算**：支付 SDK、回调验签、服务端账本、实际退款均未接入。
4. **真实定位与消息**：设备 GPS、地图服务、导航、WebSocket、短信、系统推送均未接入。
5. **完整运营管理**：线路／班次发布编辑、需求维护、扫码核销、乘车签到、调度结束及统计汇总仍需开发。
6. **高级分析与智能化**：CSV 导出、自定义统计时间段、客流预测、多车拆分、全局优化、OpenAI 等模型服务未实现。
7. **生产交付**：跨客户端并发事务、服务端权限安全验证、负载测试和各原生平台正式发布配置仍需完善。

## 3. 技术栈与项目结构

| 项目 | 当前配置 |
| --- | --- |
| 工程 | 单一 Flutter 应用，包名 `school_bus_app`，版本 `1.0.0+1` |
| Flutter | CI 固定 `3.47.9` stable；建议开发与 CI 对齐 |
| Dart | SDK 约束 `^3.11.5` |
| 状态管理 | `flutter_riverpod: ^3.3.1`，Notifier 承载业务操作 |
| 路由 | `go_router: ^17.2.2` |
| 浏览器接口 | `web: ^1.1.1`，用于 localStorage 等能力 |
| 测试 | Flutter SDK 内置 `flutter_test` |
| 代码生成 | 当前没有 build_runner、freezed、json_serializable |
| 发布 | GitHub Actions 构建 Flutter Web，GitHub Pages 托管静态产物 |

```text
lib/
├── main.dart                         # APP_MODE、初始入口与持久化注入
├── app.dart                          # AppRoot 与主题、路由
├── core/
│   ├── models/                       # 用户、车次、预约、支付、调度等模型
│   ├── providers/                    # 认证、入口、通知状态
│   ├── persistence/                  # 浏览器存储、内存实现与变化事件
│   ├── router/                       # 路由和角色重定向
│   └── theme/                        # 全局主题
├── features/
│   ├── auth/                         # 登录页面与固定账号仓库
│   ├── passenger/                    # 预约、支付、乘客工作台
│   ├── driver/                       # 司机任务、模拟位置、司机工作台
│   └── admin/                        # 运力管理、调度、后台工作台
└── shared/widgets/                   # 入口切换、重置、公共组件
test/                                 # Widget、业务规则与回归测试
.github/workflows/flutter-ci-cd.yml    # 验证、Web 构建与 Pages 部署
supabase/                             # 预备 SQL，尚未接入 App
tools/build_overleaf.py                # 综合报告打包与一致性检查

docs/                                 # 保留的历史上传资料
```

典型业务数据流为：**页面 → Notifier 业务校验与状态修改 → Provider 通知页面刷新 → state codec 编解码快照 → DemoPersistence 保存**。各域的 `mock_*_repository.dart` 提供初始样例；恢复快照后，在此基础上继续操作。

乘客、司机、后台分别维护自己的状态。相同的路线名称或车辆 ID 不代表三者已连接同一数据库。通知与信用分另有独立状态。

## 4. 本地开发与运行（供开发机使用）

本节是后续在开发机上使用的参考命令。当前阅读和演示准备使用的机器不是开发机，无需在此安装、升级或配置 Flutter；直接通过 GitHub Pages 演示即可。

### 4.1 环境准备

安装可用的 Flutter SDK 与目标平台工具；演示 Web 需要 Chrome。先确认命令实际指向的 SDK，再安装依赖：

```bash
flutter --version
dart --version
flutter doctor
flutter pub get
```

锁文件使用 `https://pub.flutter-io.cn`。如果新 SDK 自动改写 `pubspec.lock` 或 `analysis_options.yaml`，先检查是否属于本次工作，避免混入无关工具迁移。无需启动数据库、配置支付账号或运行代码生成命令。

### 4.2 运行三种初始入口

以下命令任选一条运行：

```bash
# 乘客端（不传 APP_MODE 时也默认乘客）
flutter run -d chrome --dart-define=APP_MODE=passenger

# 司机端
flutter run -d chrome --dart-define=APP_MODE=driver

# 后台管理端
flutter run -d chrome --dart-define=APP_MODE=admin
```

`APP_MODE` 是编译期参数，只决定初始入口，不是三个独立工程，也不是 URL 参数；运行后仍能通过界面切换角色。原生设备已连接时，可将 `-d chrome` 替换为对应设备，或省略后选择设备。

### 4.3 平台边界

仓库包含 Android、iOS、Web、Windows、macOS、Linux 工程文件，不表示六个平台均完成真机验收。Android 的 Java／Kotlin 目标为 17；release 仍使用 debug 签名和示例 applicationId，不能直接作为生产发行配置。Windows／Linux 可执行名由各平台顶层 CMake 的 `BINARY_NAME` 控制。

## 5. 数据保存、同步与重置

| 状态 | 保存内容 |
| --- | --- |
| `passenger` | 车次、预约、模拟付款流水 |
| `driver` | 司机任务、统计周期选择、有限位置历史 |
| `admin` | 后台车辆、司机、需求、调度方案及相关状态 |
| `notifications` | 应用内通知，最多 200 条 |
| `scores` | 信用分；退出再登录不会恢复初始分 |

Web 使用 `localStorage`，键前缀为 `school-bus-demo.v1.`。同一浏览器存储环境、同源标签页通过 `storage` 事件同步业务快照；多个标签页同时写入没有服务端事务或并发合并保证。不同设备、浏览器或隔离配置文件不共享数据，localhost 与 Pages 也不共享。

原生端、默认测试容器、浏览器禁止持久化时使用内存。登录会话与密码不持久化。司机位置历史最多保存 200 条，避免持续增长。

登录页提供“重置演示数据”，二次确认后清除当前演示修改、恢复初始样例并登出；同源其他标签页也会接收重置信号。重置适合重新演练，**不要在需要保留当前操作记录时点击**。

**演示当天需要重新初始化样例时间。** 车次和需求首次生成时使用“当前时间 + 偏移”，保存后不会因跨天或刷新自动延期。今晚预约或调度留下的数据，明天可能已经过期；正式开始前重置一次，然后再登录各角色。

## 6. 核心业务规则与修改注意事项

### 6.1 预约、支付和信用

- `BookingStatus` 只有 `pending`（待发车）、`completed`、`cancelled`；`BookingPaymentStatus` 独立包含 `unpaid`、`processing`、`paid`、`refunded`。支付成功仍是待发车，不能新增或假设 `BookingStatus.paid`。
- 剩余座位同时扣除 `TripModel.bookedSeats` 的预占座位与新增有效预约，不能再把这些预约加回 `bookedSeats` 重复扣减。
- 同用户同车次已有有效预约时拒绝重复预约；座位占用、已满座和已发车均应拒绝。
- 取消时按 `departureTime.difference(now).inMinutes` 判断：整数分钟数 **≤120 扣 5 分，否则扣 2 分**。
- 支付处理中重复提交应拒绝；处理中取消将流水标为 `failed`、预约支付状态恢复 `unpaid`；已支付取消时预约和付款流水都标为退款。
- 延迟支付回调必须检查 Provider 未销毁、当前尝试仍有效，避免覆盖取消或其他标签页的新状态。

### 6.2 调度与司机状态

- 智能建议只选择空闲且已绑定司机的车辆，每批不重复用车或司机；一个需求只匹配一辆车，不做多车拆分。
- 生成方案只是建议；调用 `confirmDispatchPlan` 后才将需求设为已分配、车辆设为运行中并加入后台模拟位置。
- 创建和确认共用容量、司机占用、双向绑定、需求状态与时间校验；确认时还需重验人数、路线、时间等建议快照。
- 司机退出、切角色、完成任务或销毁 Provider 时释放定位 Timer；重登后可恢复进行中任务的模拟位置更新。

### 6.3 扩展开发

新增持久化字段时，同步更新对应 `*_state_codec.dart` 的编码、恢复与兼容处理。订阅存储变化的 Provider 要处理业务 key 和 `'*'` 重置，并在销毁时释放订阅。

`appRouterProvider` 保持同一个 GoRouter 实例，仅在用户身份／角色或入口变化时刷新重定向，销毁时释放。不要因为信用分或 loading 变化重建路由。新增状态或异步操作时，应检查退出、销毁、重置和跨标签页更新后的迟到回调。

- `--base-href /BUS-FLUTTER/` 的首尾斜杠要保留，否则项目子路径下可能无法正确加载资源。
- 演示从根网址进入并在页面切角色。当前线上使用 `#/login` 等 hash 路由，不要手动拼接 `/BUS-FLUTTER/admin` 等不存在的静态路径。
- Pages 提供静态前端托管。当前数据保存来自浏览器，不是 GitHub 提供了数据库。

## 9. 明天现场演示脚本（约 10 分钟）

### 9.1 开场前准备

1. 用准备投屏的电脑和浏览器打开在线地址，提前等待资源加载完成。
2. 在登录页点击“重置演示数据 → 确认重置”，重新生成有效时间和初始业务状态；如果已登录，先退出。
3. 确认三种快捷账号能登录，并熟悉工作台的上下滚动位置。正式演示前再重置一次，确保下面预期数字成立。
4. 以同一浏览器为主完成演示。若准备多标签页，统一重置后再分别登录；不要依赖手机与电脑共享业务状态。
5. 本机以已部署的 Pages 为演示入口，无需搭建开发环境；提前保存一次成功彩排的录屏和截图作为网络异常时的备用材料。若另用自己的开发机，可在那里按第 4 节提前验证本地运行。

开场可直接说：

> 这是一个使用 Flutter 开发的校车管理系统，目前实现了乘客、司机和管理员三种角色的主要交互流程。这个版本使用本地样例和浏览器存储，下面展示预约、司机任务和后台调度；支付、位置与智能调度分别采用模拟支付、模拟轨迹和本地规则算法。

### 9.2 乘客：预约 → 支付 → 取消退款（约 3 分钟）

| 步骤 | 操作 | 预期现象／讲解点 |
| --- | --- | --- |
| 1 | 点击用户端快捷账号 `13800000001`，再点登录 | 初始信用分 **96**；大学城早班线余座 **27/45** |
| 2 | 展示车次列表和已满座的“校区环线” | 展示路线、发车时间、票价与满座禁用状态 |
| 3 | 大学城早班线 → 预约选座 → 选 **19 座** → 确认预约 | 余座 **27 → 26**，新增待发车／待支付预约，车次显示已预约 |
| 4 | 我的预约 → 立即支付 → 选择微信或支付宝 → 确认支付 | 约半秒后变为已支付，预约仍待发车；生成支付通知 |
| 5 | 取消预约 → 确认取消 | 恢复余座 **27**，订单已取消／已退款，信用分 **96 → 91** |
| 6 | 展示通知或信用记录 | 说明取消距发车两小时内扣 5 分，退款为模拟状态 |

以上以刚重置的样例为前提：早班线在初始化后约 1 小时 40 分发车。选座界面不是全部座位都空闲，19 座是此初始数据的可用座位。

可选加分项：刷新后重新登录乘客，展示信用分 91 和取消退款记录仍在，说明“业务记录保存在当前浏览器，登录会话不保存”。不要把刷新后重登当成故障。

### 9.3 司机：查看名单 → 开始 → 模拟位置 → 完成（约 2 分钟）

| 步骤 | 操作 | 预期现象／讲解点 |
| --- | --- | --- |
| 1 | 切司机入口，选择 `13800000002` 并登录 | 初始 3 个待发车任务，共 9 名样例乘客 |
| 2 | 展开大学城早班线的“乘客名单与上车点” | 展示姓名、手机尾号、上车点与座位 |
| 3 | 点击“开始任务并共享位置” | 任务进入行程中，立即生成第 1 条位置记录 |
| 4 | 到“实时位置共享”，等约 5 秒或点击“立即上报位置” | 坐标、速度、更新时间与记录数变化；说明为模拟轨迹 |
| 5 | 点击“到站完成” | 任务变已完成，位置共享停止，可启动其他任务 |
| 6 | 时间允许时切换日／周／月 | 展示统计视图，并说明数据为固定样例 |

这里展示的是司机自己的样例任务，**不是刚才乘客预约自动派发的任务**。完成司机任务不会让乘客预约同步变为已完成。

### 9.4 后台：生成建议 → 确认调度 → 查看监控（约 3 分钟）

| 步骤 | 操作 | 预期现象／讲解点 |
| --- | --- | --- |
| 1 | 切后台入口，选择 `13800000003` 并登录 | 初始 4 辆车：运行 2、空闲 1、维修 1；3 位司机、待调度 82 人 |
| 2 | 展示车辆、司机与绑定情况 | 指出 **校A·2036，38 座，赵师傅** 是初始唯一可自动匹配的空闲资源 |
| 3 | 滚到“车次调度”，点击“AI 生成方案” | 生成大学城早班线 **36 人**的待确认方案，满载率约 **95%** |
| 4 | 点击“确认生效” | 运行车辆 **2 → 3**、空闲车辆 **1 → 0**、待调度人数 **82 → 46** |
| 5 | 查看实时位置监控，选中车辆并点击“刷新位置” | 展示司机、坐标、速度和时间；说明是网格地图与模拟位置 |

只生成一条建议是初始资源限制的正常结果；确认后若未增加空闲车辆和绑定司机，再次生成会提示无可用资源。不要在主流程前删除、换绑或占用校A·2036与赵师傅。

如果老师要求展示增删改或人工调度，可追加：新增空闲车辆“校A·5098／测试车型 T1／30 座”，新增司机“孙师傅／13800009001／A1-TEST-9001”并绑定该车；在“科技园通勤线 28 人”中选择人工调度、新车和新司机，生成方案后确认。新增司机是后台管理资料，不能用其手机号登录。

## 10. 演示故障排查

| 现象 | 原因与处理 |
| --- | --- |
| 一打开就是后台 | 这是 Pages 的初始入口配置；直接点击用户／司机快捷账号切换 |
| 点快捷账号没有进入主页 | 账号只被填入，还需点击“登录” |
| 提示账号与入口不匹配 | 选择对应角色快捷账号，再登录 |
| 车次已过期、无法预约或需求不能调度 | 旧时间被浏览器保存；回到登录页确认重置后重新演示 |
| 信用分不是 96，或司机任务已完成 | 之前操作已持久化；正式演示前重置 |
| AI 只生成一条，或确认后无法再生成 | 初始仅一辆空闲且绑定司机的车；新增并绑定资源，或重新开始演练 |
| 刷新后返回登录页 | 登录会话不持久化，重新登录即可查看已保存业务状态 |
| 图表没有随订单增加而变化 | 历史分析和司机统计目前是固定样例 |
| 打开网站空白或仍是旧版 | 先确认网络、等待 Flutter 资源加载；检查 Actions 部署成功及 base-href，必要时重新加载页面 |
| 非开发机无法运行 Flutter 检查 | 演示直接使用 Pages；环境检查和修复留到自己的开发机进行 |

## 11. 预备数据库与课程资料

`supabase/` 仅保留建表、约束、RLS 与种子 SQL；Flutter 中没有 Supabase 客户端，不读取 `BACKEND` 或 `SUPABASE_*`。**启动当前 App 和测试不需要先初始化 Supabase**，也不存在切一个参数就可启用真实后端的实现。

若单独验证 SQL，按“执行迁移建表 → 创建种子文件头部指定的三个 Auth 用户 → 执行 seed”的顺序，在开发实例中验证。现有 SQL 还需要权限与事务审查，不能直接当作生产服务接入完成的证据。

本 README 用于开发和演示；课程综合报告仍在根目录 `main.tex`，交付包为 `overleaf.zip`。`docs/` 保留历史上传资料，其中截图、日期、测试数字与后端方案不自动代表当前实现。报告使用 XeLaTeX、`ctexrep` 的 Fandol 字体，无需系统中文字体、minted 或 shell-escape。

修改 `main.tex` 或 `report-assets/` 后重建并检查报告归档：

```bash
python3 tools/build_overleaf.py
python3 tools/build_overleaf.py --check
```

仅修改 README 不需要重打报告包。导入 Overleaf 后主文件选 `main.tex`，编译器选 **XeLaTeX**；本地安装对应工具后可执行：

```bash
latexmk -xelatex -outdir=build/report main.tex
```
